# Decision Log
In creating this package, which is meant for a wide range of use cases, we had to take opinionated stances on a few different questions we came across during development. We've consolidated significant choices we made here, and will continue to update as the package evolves.

## Resolving "API Key" to `project_api_key`
The OpenAI connector syncs multiple key tables. Usage and cost records reference project-scoped key identifiers, which matches `project_api_key`, not the org-level `admin_api_key` table. This package joins on `project_api_key` wherever an "API key" dimension is needed. `admin_api_key` is out of scope for now — if you need an admin-key audit dimension, please open a GitHub issue.

## Cost Attribution: Direct When Available, Inferred Otherwise, With a Completeness Guarantee
When the OpenAI Costs API reports a project_id directly on a cost row, `openai__cost_usage_report` uses it as-is (`cost_attribution_method = 'direct'`). When it doesn't, this package derives an implied per-token rate from the Costs endpoint's daily unattributed spend per model and token unit type — using only the completion volume from projects that don't already have direct cost that day, so already-paid-for tokens don't dilute the rate — then applies that rate to each remaining project's share of that day's token volume (from the Usage API's `completion` data) — `cost_attribution_method = 'allocated'`.

Not every dollar of cost can be tied to a project and model this way. Non-token charges (e.g. "Assistants API") don't break out by token type, and are carried at the org level with `cost_type = 'other'` and `cost_attribution_method = 'unallocated'` (if no project) or `'direct'` (if a project is present). When the line item is a bare model name (e.g. `text-embedding-3-large`, `GPT-4o`, `OpenAI o1`), that name becomes the row's `model`; otherwise `model` is null. Only token-billed models are named this way. Models billed in other units, such as `whisper`, and category or feature line items, such as `Embedding models` or `Assistants API`, keep a null `model` and stay in `other`. Separately, some token-type costs have no completion counterpart at all. For example, the Completions API never reports cache-write token volume, so `cache_write` costs and some completion volume have no cost data at all. Both surface as their own row with `cost_attribution_method = 'unmatched'` rather than being silently dropped, so `sum(openai_cost)` always ties out to the total in the source `cost` table.

## Cost and Usage Report in Long Format, Not Wide
`openai__cost_usage_report` is one row per (source relation, day, project, model, `token_unit_type`) rather than pivoting `input`/`cache_read`/`output`/`cache_write` into separate columns. This mirrors Fivetran's Claude/Anthropic package, which reports token types the same way. A wide shape would have no column for `cache_write` at all, since it has no matching completion volume to populate a token-count column with — the long shape gives every token unit type, including ones with cost but no usage data (or vice versa), a natural place to appear as its own row instead of being folded into a model-less `other` bucket or dropped.

## Partial Cost and Code Reporting
`openai__cost_usage_report` and `openai__code_report` are each built from two optional source-table pairs. Rather than requiring both tables in a pair to be enabled, each model still produces useful, differently-shaped output with only one side enabled — the columns that depend on the disabled table are omitted entirely from the output (not nulled), rather than the whole model being disabled. See [Partial cost and code reporting](https://github.com/fivetran/dbt_openai/blob/main/README.md#partial-cost-and-code-reporting) in the README for the exact behavior per variable.

## Codex Model/Speed Detail Is Rolled Up, Not Fanned Out
`codex_usage_model` reports Codex Enterprise credit and token consumption at a (day, user, model, speed) grain, one level finer than `codex_usage`'s (day, user) grain. Rather than fanning `openai__code_report` out to one row per model/speed — which would repeat day-level productivity metrics across every model/speed row, risking downstream double-counting — the model/speed breakdown is summed onto the (day, user) grain instead. `codex_usage` also reports its own day-level credit/token totals directly, so those are used as the primary source when it's enabled; `codex_usage_model`'s rollup only serves as a fallback when `codex_usage` is disabled, and as the source of `count_models_used`, which only it can report.

## Compliance Platform Cost Data Is Its Own End Model, Cost-Only
This package also models cost data from Compliance Platform (ChatGPT Enterprise), synced as part of the same connector as the rest of this package's OpenAI Platform data: `stg_openai__compliance_cost`, `stg_openai__compliance_cost_billing`, `stg_openai__compliance_users`, and `openai__compliance_cost_report`. Only cost data is modeled — no conversation, audit, or auth log data — gated behind `openai__using_compliance_cost` and `openai__using_compliance_users`, both defaulting to `true`.

It's a separate end model rather than folded into `openai__code_report`: only its `codex` and `work` product rows cover the same activity as `openai__code_report` (and even then from a cost angle, not `openai__code_report`'s productivity angle — lines of code, threads, turns), while its `chat` and `image` product rows are ChatGPT Enterprise usage nothing else in this package reports at all. A user who queries both reports and sums `credits`/spend across them will double-count Codex spend — that's a documented caution, not a reason to merge the two models.

## Compliance Cost Events Are Restated, Not Deduplicated by the Connector
OpenAI re-emits a still-open cost event in every later Compliance log file covering its hour, each time with a cumulative token count, so `stg_openai__compliance_cost` can carry more than one row per (event_id, organization_id). The connector does not collapse this to one row itself. Summing across those rows overstates usage; picking an arbitrary one keeps a possibly-stale snapshot. `openai__compliance_cost_report` resolves this by joining to `stg_openai__compliance_costs_log_file` and keeping only the row from the log file with the latest `end_time` per event. Billing (`stg_openai__compliance_cost_billing`) is keyed on (event_id, organization_id, sku) with no log file id, so it joins to that event on `event_id` and `organization_id` alone.

## Compliance Cost Is Split by Unit, Never Summed Across Units
OpenAI switched the Compliance cost log from credits to USD on 2026-10-10, recording the unit in `cost_unit`. Summing `cost_value` across the switch would add credits to dollars, so staging splits it into `credits` and `cost_usd` by `cost_unit`, and `openai__compliance_cost_report` sums each separately. OpenAI's own `estimated_cost_usd_amount` is only populated on credit rows and reflects list price, which can differ from a customer's contract, so it isn't used to bridge the two. Instead, customers who set `openai__credit_rate` (USD per credit) get `total_cost_usd`, which prices credits at that rate and adds USD as is. `cost_unit` stays in the report's grain, since both units appear on 2026-10-10 itself.

## Compliance Rollback Events Are Kept, Not Filtered
OpenAI corrects the Compliance cost log by adding rollback events (event_id `costapi_rollback_...`) with negative cost and tokens that cancel earlier events, then re-sending the corrected usage as new events. For usage on 2026-11-02 to 2026-11-05, for example, OpenAI first sent about four times as many smaller events, then rolled them back and re-sent the same usage at the usual event size. All three sets of events stay in the log. `openai__compliance_cost_report` keeps every event, including negative ones, so the rollbacks net out the events they reverse and daily totals match OpenAI's log. Filtering out rollbacks or negative cost would count the reversed usage twice.

## Compliance Products Are Lowercased and Not Allowlisted
From 2026-11-02, OpenAI sent some events with lowercase product names (`ChatGPT` became `chatgpt`, `Work` became `work`) while others kept the original casing, and new products appeared (`hermes`, `chatgpt_agent`, `site_hosting`, `orbit`). Staging lowercases `product` so each product groups as one value. The package reports every product in the log rather than a fixed list, so a new product shows up in `openai__compliance_cost_report` instead of being dropped. SKU names changed format on 2026-10-10 and again on 2026-11-02; the package passes `sku` through as is and documents the shared phrases for parsing the token type.

## Column Naming Aligned With Fivetran's Claude/Anthropic Package
This package is designed to eventually roll up alongside a Claude/Anthropic usage package into a shared multi-vendor AI reporting package. Where the underlying concepts match, column names were deliberately aligned with the equivalent columns in Fivetran's Claude/Anthropic dbt package: `source_relation`, `date_day`, `actor_user_id`, `actor_email`, `openai_cost`, `currency`, and `cost_type`. Columns with no real Claude/Anthropic equivalent (for example, `project_role_count` and `org_permission_roles`, which reflect OpenAI-specific organization structures) were left as-is rather than forced into an artificial alignment.

## Model Names Retain Family and Variant Separately
Reports keep the original `model` and add structural `model_family` and `model_variant` columns. Families retain numeric GPT and o-series version lines, such as `gpt-4o`, `gpt-5.2`, and `o4`; known named product prefixes also form families. Parsing lowercases and trims the name, unwraps fine-tuned `ft:` names, and strips a trailing YYYY-MM-DD-shaped snapshot suffix. The remaining suffix becomes the variant, with compound values such as `deep-research` preserved intact. Unrecognized names use the original model as their family and a null variant; recognized names without a suffix also have a null variant. Exact customer family overrides take precedence but do not alter how variants are parsed. Neither field asserts architecture, capabilities, or billing rates, and report grain remains based on the original model.

## Usage Totals Preserve Known Components

Completion input tokens exclude cached input, so total tokens are input plus cache-read plus output tokens. OpenAI occasionally reports a negative completion row that backs out earlier usage; we keep its values signed rather than flooring them at 0 or dropping the row, so totals tie out to the source. If only one component is populated, the report retains that known quantity; if both are missing, the total remains null. Web and file search use tool-call counts in the shared request-count column. Products metered in other units retain null token quantities.

## Codex Credit Cost Is Estimated From a Customer-Set Rate, Not Derived

`openai__code_report`'s `estimated_cost_amount` multiplies `credits` by `openai__credit_rate`, a variable the customer sets themselves in USD per credit; the source data has no universal credits-to-USD rate to read directly. The same variable prices credits in `openai__compliance_cost_report`, since Codex and Compliance credits are the same unit. `openai__code_report_credit_rate`, its earlier name, is still read when `openai__credit_rate` isn't set. An implied rate could instead be derived from OpenAI's `estimated_cost_usd_amount`, but that reflects list price rather than the customer's contract. The column is omitted (not nulled) when the rate variable isn't set.

## Codex Credits Are Null, Not Zero, When the Source Reports None

The Codex Analytics API stopped returning credits on 2026-10-10, while tokens and productivity metrics kept arriving. `openai__code_report` leaves `credits` and `estimated_cost_amount` null in that case rather than coalescing to 0, which would read as free usage. Codex cost from that date is in `openai__compliance_cost_report` (products `codex` and `work`). The package doesn't fill `openai__code_report` from the compliance log, for the reasons in [Compliance Platform Cost Data Is Its Own End Model, Cost-Only](#compliance-platform-cost-data-is-its-own-end-model-cost-only).
