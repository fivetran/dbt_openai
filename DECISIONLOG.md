# Decision Log
In creating this package, which is meant for a wide range of use cases, we had to take opinionated stances on a few different questions we came across during development. We've consolidated significant choices we made here, and will continue to update as the package evolves.

## Every Source Table Is Variable-Guarded, Except `users`
Different customers configure their OpenAI connector with different combinations of Admin, Project, and Codex Enterprise API keys, and each key type only unlocks a subset of the connector's tables — no single table is common enough to leave unguarded. So every source table this package can use is gated behind its own `openai_using_<table>` variable, defaulting to `true`, with one exception: `users` is the spine of `openai__user_summary`, with no partial-value fallback if it's missing, so `stg_openai__users` and every model that reads from it always build — there's no `openai_using_users` variable at all. See the README's [Enable/Disable models](README.md#enabledisable-models) section for the full list.

## Resolving "API Key" to `project_api_key`
The OpenAI connector syncs multiple key tables. Usage and cost records reference project-scoped key identifiers, which matches `project_api_key`, not the org-level `admin_api_key` table. This package joins on `project_api_key` wherever an "API key" dimension is needed. `admin_api_key` is out of scope for now — if you need an admin-key audit dimension, please open a GitHub issue.

## Cost Attribution: Direct When Available, Inferred Otherwise, With a Completeness Guarantee
When the OpenAI Costs API reports a project_id directly on a cost row, `openai__cost_usage_report` uses it as-is (`cost_attribution_method = 'direct'`). When it doesn't, this package derives an implied per-token rate from the Costs endpoint's daily unattributed spend per model and token unit type — using only the completion volume from projects that don't already have direct cost that day, so already-paid-for tokens don't dilute the rate — then applies that rate to each remaining project's share of that day's token volume (from the Usage API's `completion` data) — `cost_attribution_method = 'allocated'`.

Not every dollar of cost can be tied to a project and model this way. Non-token charges (e.g. "Assistants API") don't break out by model at all, and are carried at the org level with `cost_type = 'other'` and `cost_attribution_method = 'unallocated'` (if no project) or `'direct'` (if a project is present). Separately, some token-type cost has no completion counterpart at all — for example, `cache_write` cost, since the Completions API never reports cache-write token volume — and some completion volume has no cost data at all; both surface as their own row with `cost_attribution_method = 'unmatched'` rather than being silently dropped, so `sum(openai_cost)` always ties out to the total in the source `cost` table.

## Cost and Usage Report in Long Format, Not Wide
`openai__cost_usage_report` is one row per (source relation, day, project, model, `token_unit_type`) rather than pivoting `input`/`cache_read`/`output`/`cache_write` into separate columns. This mirrors Fivetran's Claude/Anthropic package, which reports token types the same way. A wide shape would have no column for `cache_write` at all, since it has no matching completion volume to populate a token-count column with — the long shape gives every token unit type, including ones with cost but no usage data (or vice versa), a natural place to appear as its own row instead of being folded into a model-less `other` bucket or dropped.

## Partial Cost and Code Reporting
`openai__cost_usage_report` and `openai__code_report` are each built from two optional source-table pairs. Rather than requiring both tables in a pair to be enabled, each model still produces useful, differently-shaped output with only one side enabled — the columns that depend on the disabled table are omitted entirely from the output (not nulled), rather than the whole model being disabled. See [Partial cost and code reporting](README.md#partial-cost-and-code-reporting) in the README for the exact behavior per variable.

## Codex Model/Speed Detail Is Rolled Up, Not Fanned Out
`codex_usage_model` reports Codex Enterprise credit and token consumption at a (day, user, model, speed) grain, one level finer than `codex_usage`'s (day, user) grain. Rather than fanning `openai__code_report` out to one row per model/speed — which would repeat day-level productivity metrics across every model/speed row, risking downstream double-counting — the model/speed breakdown is summed onto the (day, user) grain instead. `codex_usage` also reports its own day-level credit/token totals directly, so those are used as the primary source when it's enabled; `codex_usage_model`'s rollup only serves as a fallback when `codex_usage` is disabled, and as the source of `count_models_used`, which only it can report.

## Compliance Platform Cost Data Is Its Own End Model, Cost-Only
This package also models cost data from Compliance Platform (ChatGPT Enterprise), synced as part of the same connector as the rest of this package's OpenAI Platform data: `stg_openai__compliance_cost`, `stg_openai__compliance_cost_billing`, `stg_openai__compliance_users`, and `openai__compliance_cost_report`. Only cost data is modeled — no conversation, audit, or auth log data — gated behind `openai_using_compliance_cost` and `openai_using_compliance_users`, both defaulting to `true`.

It's a separate end model rather than folded into `openai__code_report`: only its `codex` product rows cover the same activity as `openai__code_report` (and even then from a cost angle, not `openai__code_report`'s productivity angle — lines of code, threads, turns), while its `chat` and `image` product rows are ChatGPT Enterprise usage nothing else in this package reports at all. A user who queries both reports and sums `credits`/spend across them will double-count Codex spend — that's a documented caution, not a reason to merge the two models.

## Compliance Cost Events Are Restated, Not Deduplicated by the Connector
OpenAI re-emits a still-open cost event in every later Compliance log file covering its hour, each time with a cumulative token/credit count, so `stg_openai__compliance_cost`/`_billing` can carry more than one row per (event_id, organization_id) — the connector does not collapse this to one row itself. Summing across those rows overstates spend; picking an arbitrary one keeps a possibly-stale snapshot. `openai__compliance_cost_report` resolves this by joining to `stg_openai__compliance_costs_log_file` and keeping only the row from the log file with the latest `end_time` per event, before joining billing.

## `project_role` and `groups` Are Not Modeled
Neither table has a user dimension, so neither can feed `openai__user_summary` or any other end model. `project_role` is a project's catalog of custom role *definitions* — every field a user report would need (role name, `predefined_role`, `resource_type`) is already available per-assignment on `project_user_role`, which this package does model. `groups` has no synced membership bridge table either, so there's no way to compute a per-user group count or list from what's available. Out of scope for now, similar to `admin_api_key` above — if a membership table is added to the connector in the future, or you need one of these as a standalone catalog, please open a GitHub issue.

## Column Naming Aligned With Fivetran's Claude/Anthropic Package
This package is designed to eventually roll up alongside a Claude/Anthropic usage package into a shared multi-vendor AI reporting package. Where the underlying concepts match, column names were deliberately aligned with the equivalent columns in Fivetran's Claude/Anthropic dbt package: `source_relation`, `date_day`, `actor_user_id`, `actor_email`, `openai_cost`, `currency`, and `cost_type`. Columns with no real Claude/Anthropic equivalent (for example, `project_role_count` and `org_permission_roles`, which reflect OpenAI-specific organization structures) were left as-is rather than forced into an artificial alignment.

## Model Names Retain Family and Variant Separately
Reports keep the original `model` and add structural `model_family` and `model_variant` columns. Families retain numeric GPT and o-series version lines, such as `gpt-4o`, `gpt-5.2`, and `o4`; known named product prefixes also form families. Parsing lowercases and trims the name, unwraps fine-tuned `ft:` names, and strips a trailing YYYY-MM-DD-shaped snapshot suffix. The remaining suffix becomes the variant, with compound values such as `deep-research` preserved intact. Unrecognized names use the original model as their family and a null variant; recognized names without a suffix also have a null variant. Exact customer family overrides take precedence but do not alter how variants are parsed. Neither field asserts architecture, capabilities, or billing rates, and report grain remains based on the original model.

## `openai_model_family_overrides` Is a List, Not a Dictionary
`openai_model_family_overrides` takes a list of `{model, family}` objects rather than a `{model: family}` dictionary — a clearer shape that also leaves room to add a `variant` override key later without another breaking format change. It's still excluded from `.quickstart/quickstart.yml`'s `supported_vars`, though: Quickstart's dictionary type only renders as a Value/Alias pair (the shape passthrough metric variables need), and the tooling that maintains `supported_vars` only knows how to render list items shaped like that same `name`/`alias` pair — not arbitrary object keys like `model`/`family`. Customers who need this still set it directly in `dbt_project.yml`.

## Usage Totals Preserve Known Components
Completion input tokens include cached input, so total tokens are input plus output without adding cache-read tokens again. If only one component is populated, the report retains that known quantity; if both are missing, the total remains null. Web and file search use tool-call counts in the shared request-count column. Products metered in other units retain null token quantities.
